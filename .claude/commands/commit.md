# Commit

Проанализируй изменения в репозитории и создай коммит с правильным сообщением и обновлённой версией приложения.

## Шаги

1. **Изучи изменения.** Выполни параллельно:
   - `git status` — список изменённых файлов
   - `git diff HEAD` — содержимое изменений (staged + unstaged)
   - `git log --oneline -5` — последние коммиты для стиля

2. **Сформируй сообщение коммита** по правилам:
   - Формат: `<type>: <описание на русском языке>`
   - Типы: `feat` (новая функция), `fix` (исправление), `refactor` (рефакторинг), `style` (UI/стили), `chore` (зависимости, конфиг), `perf` (оптимизация)
   - Описание: краткое, конкретное, в инфинитиве («добавить», «исправить», «переместить»)
   - Если изменения разнородные — использовать `chore: обновление` или перечислить главное

3. **Определи тип версионного бампа** на основе изменений:
   - `patch` (0.0.X) — исправления, рефакторинг, стили, мелкие правки
   - `minor` (0.X.0) — новая функциональность, новые страницы/фичи
   - `major` (X.0.0) — только если явно сломана обратная совместимость (очень редко)

4. **Обнови версию в `package.json`:**
   - Прочитай текущую версию из `package.json`
   - Вычисли новую версию согласно типу бампа
   - Обнови поле `"version"` в `package.json`

5. **Создай коммит:**
   - Добавь в стейдж все изменения: `git add -A`
   - Создай коммит с сообщением в формате: `<type>: <описание> [v<новая_версия>]`
   - Например: `feat: добавить фильтрацию тренировок по дате [v5.16.0]`

6. **Выведи итог:** тип бампа, старая → новая версия, финальное сообщение коммита.

## Важно
- Не пушь в remote без явной просьбы
- Если нет изменений (`git status` чист) — сообщи об этом и не создавай пустой коммит
- Всегда передавай сообщение коммита через HEREDOC во избежание проблем с кавычками
